# 意思決定ログ (Decision Log)

- プロジェクト研究A「RemixIT × TF-Locoformer によるシングルチャネル音源分離」の意思決定記録
- 各決定は「背景 → 選択肢 → 決定 → 理由」の形で残す
- 成果発表期限: 2026-08-10

## DEC-001: 研究テーマの大枠 (2026-07-20)

- 状態: 決定
- 決定: RemixIT の自己学習の枠組みに TF-Locoformer をモデルとして組み込み、シングルチャネルの音源分離(音声強調)に取り組む
- 背景: 研究室仮配属のプロジェクト研究Aのテーマとして学生が選定した
- 理由:
  - RemixIT は使うモデルの種類を選ばないと論文で明言されており、組み合わせは手法として妥当
  - RemixIT の元論文は軽量な時間領域モデル(Sudo rm -rf、パラメータ数0.56M)だけで検証している。性能の高いモデルで自己学習がどう振る舞うかは確かめられておらず、小さくても新しさがある
  - TF-Locoformer は公式実装が公開されており、実装のリスクが低い

## DEC-002: タスク設定(音声強調 vs 話者分離) (2026-07-20)

- 状態: 決定 — (b) 2話者分離
- 選択肢:
  - (a) 音声強調(音声とノイズの2出力): RemixIT が本来想定する設定。ノイズ推定の入れ替えによる混ぜ直しがそのまま使える
  - (b) 2話者分離: TF-Locoformer が最も強い分野だが、RemixIT の混ぜ直し(ノイズだけ入れ替える)を話者の入れ替えに読み替える拡張が必要
- 決定: 2話者分離に取り組む(ユーザー選択)
- 理由・注意点:
  - TF-Locoformer が最も強い分野であり、既存の分離ベンチマークと比較しやすい
  - 混ぜ直しは「バッチの中で片方の話者の推定をランダムに入れ替えて混ぜ直す」に拡張する。生徒の損失は、話者の割り当てを考慮した損失(PIT)とSI-SNRを組み合わせる
  - 関連研究に注意: TF-Locoformer の筆頭著者である Saijo らが Self-Remixing(ICASSP 2023)という、混ぜ直しを使った正解なしの話者分離をすでに発表している(こちらは混合音を作り直せているかを見る損失であり、RemixIT の「音源ごとの疑似的な正解を使う損失+教師の継続更新」とは異なる)。本プロジェクトは「RemixIT型(音源ごとの疑似的な正解+教師の継続更新)× TF-Locoformer」として違いを明確にし、発表では必ずこの関連研究に触れる

### 候補の比較 (2026-07-20 検討)

| 観点 | (A) JVS の模擬混合 | (B) J-CHAT の実会話 | (C) Libri2Mix(英語) |
|---|---|---|---|
| 正解データ | あり(模擬混合なのでSI-SNRで数値評価できる) | なし(音質の自動評価や聞き比べのみ) | あり |
| RemixIT の適応の見せ方 | 英語で学習済みの教師 → 日本語への適応として分かりやすい | 実環境への適応として最も本物に近い | 英語内でのドメイン適応(先行研究の再現に近い) |
| データ準備のコスト | 低い(JVSは無料で軽く、16kHzに変換済みの資産もNASにある) | 高い(データの取得、2話者かつ重なりのある区間の選別、リサンプルが必要) | 中(LibriSpeechの取得と混合音の生成が必要) |
| 教師の調達 | MERL公開のTF-Locoformer(WHAMR!、2話者)をそのまま使える | 同左だが教師の性能低下が大きい可能性 | 公開済みのチェックポイントが多数ある |
| 8/10までのリスク | 低い | 高い(選別の実装と、数値によらない評価になる) | 中程度 |
| 発表での見せやすさ | 「英語のモデルを正解なしで日本語向けにする」で分かりやすい | 実データでのデモは強いが数値が出ない | 手堅いが、素材が借り物という印象 |

- 採用した方針: (A) JVS を土台にする。教師はMERL公開のTF-Locoformer(英語)、適応先はJVSの模擬2話者混合(正解は評価にだけ使う)、評価は話者が重ならないJVSのテストデータでSI-SNRの改善量を測る
  - 余裕があれば (B) J-CHAT の一部区間で「実会話への適用デモ(聞き比べ)」を追加の目標とする。(C) は新しさと発表の見せやすさの観点で見送る
- 前提: 使える計算資源は RTX 2080 Ti(11GB)×3(DEC-005)

> 以下は方針を決める前の検討段階のメモで、実際には採用していない(経緯として残す)。実際の構成は DEC-008(8kHz・JVS・教師候補の比較)と DEC-010(適応先を雑音つきに難しくする・WHAMR!版を採用)を正とする
> - 教師の案(不採用): SpeechBrain の sepformer-wsj02mix、Asteroid の ConvTasNet/DPRNN など、MERL以外のチェックポイント → 最終的にMERL公式のチェックポイントに統一した(TF-Locoformerでそろえる必要があるため)
> - 適応先の案(不採用): Libri2Mix(英語) → 「日本語への適応」という研究の核心が失われるため、JVSに決定した(DEC-002/003の主旨と矛盾していた記載)

## DEC-004: 実装の土台(ESPnetを使うか、独自に作るか) (2026-07-20)

- 状態: 決定 — ESPnet を土台にして手を加える
- 決定: TF-Locoformer公式(ESPnetの音声強調・分離向けの仕組み)を土台に、ESPnetに手を加える(ユーザー選択)
- 理由・注意点:
  - ESPnetにあるデータ準備・評価・TF-Locoformerの設定をそのまま使える
  - RemixITの教師・生徒のやり取り(混ぜ直し・教師の更新)はESPnetの標準の学習の仕組みには乗らないため、専用の学習スクリプトを追加で作る必要がある。ここが実装の主なリスク
  - 対策: データ準備・モデルの定義・評価はESPnetに乗せ、RemixITのやり取りの部分だけ独立したスクリプトとして書く(ESPnet本体への手直しを最小限にする)

## DEC-007: 教師の言語の違いへの対処(英語教師で大丈夫か) (2026-07-20)

- 状態: 決定(設計方針)
- 背景: 「教師も日本語のモデルでないとうまく分離できないのではないか」という懸念(ユーザー提起)
- 分析:
  - 話者分離の主な手がかり(声の高さ・声色・音の構造)は言語によらない部分が大きく、英語の教師でも追加学習なしである程度の分離は期待できる。ただし性能の低下は見込む
  - RemixITは教師の推定が不完全な状況をむしろ前提にした設計であり、元論文では教師のSI-SNRが5dB未満という低い品質の推定でも、生徒が平均で2dBほど改善することを示している(Fig. 5)。ただし教師のSI-SNRがマイナス10dB以下まで崩れている場合は、生徒も改善できないことも示されている(Fig. 3)
  - 教師を最初から日本語で本格的に学習し直すと、埋めるべき違い(研究の主題そのもの)がなくなり、「適応」の意味が消えてしまう。言語の違いは取り除くべき邪魔なものではなく、確かめたい条件として扱う
- 決定:
  1. 教師を追加学習なしで評価する実験(E0)を、進めてよいかどうかの判定に使う。英語の教師(MERL公開のTF-Locoformer)をJVSの模擬テストデータで評価し、SI-SNRの改善量が5dB程度以上なら進める(そのままRemixITへ)
  2. 5dBに届かなかった場合の代替案: 少量の正解付きJVSデータ(全体の10%程度)で教師を軽く追加学習してからRemixITを行う。この場合は「少量の正解ありデータを使う半教師あり適応」(RemixITの元論文にも同じ設定がある)として発表を組み直す。研究として成立する
  3. どちらに転んでも「教師の最初の性能と生徒の改善幅の関係」として発表で語れるため、E0の結果自体が成果になる

## DEC-008: サンプリング周波数・教師のチェックポイント・混合の条件 (2026-07-20)

- 状態: 決定
- 決定:
  1. 8kHzで統一する。MERL公開の分離用チェックポイント(WSJ0-2mix / Libri2mix / WHAMR!)はいずれも8kHzで学習されているため、JVS(16kHzに変換済みの資産)を混合音の生成時に8kHzへ変換し直す
  2. 教師の候補はWSJ0-2mix版とLibri2mix版の両方をE0で追加学習なしのまま評価し、JVSのテストデータで良い方を教師として採用する(推論だけなのでコストは小さい。「どの英語教師が日本語へうまく移るか」自体が発表で語れる副次的な結果になる)。WHAMR!版は残響前提のため優先度を下げる
  3. 混合の条件: 別の話者どうしのペア、話者間のSNRを一様分布[-5, 5]dBで振る、短い方に合わせて完全に重なる混合、学習用20,000件・検証用1,000件・評価用1,000件
- 確認済みの事実: MERLのリポジトリ(Apache-2.0ライセンス)は WSJ0-2mix / Libri2mix / WHAMR! / DNS の学習済みモデルを提供している。この作業マシンの環境(conda環境`tflocoformer`: ESPnet 202402 + TF-Locoformerのモデル + GPUが使える状態)で動くことを確認済み。JVSは16kHzへの変換・話者が重ならない分割が済んだ資産(学習用10,398・検証用1,299・評価用1,300発話)を再利用する(DEC-006の範囲内)

## DEC-009: データの置き場所(ローカルディスクが満杯だった問題への対処) (2026-07-20)

- 状態: 決定
- 背景: 研究室サーバーのルートの記憶領域(1.8TB)が100%満杯(空き199MB)だと判明した。主な原因は他ユーザーのデータ(ホームディレクトリ全体で540GB超、内容を見られない領域もある)であり、勝手に削除できない。このままではデータの生成やチェックポイントの保存がすぐに失敗する
- 決定: 本プロジェクトの容量が大きいものはすべてNAS(/mnt/kiso-qnap5/kueki/proken-A、空き52TB)に置く
  - `data/` `exp/` はリポジトリからNASへのシンボリックリンクにする
  - MERLのリポジトリ(教師のチェックポイントを含む)もNASの`third_party/`に置く
  - 8kHzの音声は容量が軽いため、NAS経由の読み書きでも学習の速度に問題はないと見込む
- 残る課題(ユーザー対応): サーバーの管理者・研究室メンバーへディスクが満杯であることを伝えることを勧める(学習とは別の問題として)

## DEC-010: 適応先を難しくする(雑音・残響を加える) (2026-07-20)

- 状態: 決定・対応済み
- 背景: E0の簡易確認(20件)で、英語WSJ0-2mix教師の追加学習なしの性能がSI-SNR改善量20.84dBと、予想を大きく上回った。クリーンな読み上げ音声どうしの混合では、言語の違い(英→日)だけではほぼ障害にならない可能性が高い。教師が最初から高性能だと、RemixITで埋めるべき違いが残らず、適応の効果を示しにくい
- 選択肢:
  1. 適応先を難しくする(本命): JVSの混合音に雑音(WHAM! noiseなど)・残響を加えた条件を適応先にする。クリーンな条件で学習した英語教師は性能が下がるはずで、RemixITの出番が生まれる。最終目的(実会話)にも近づく。データ生成・評価・教師の仕組みはそのまま使い回せる
  2. このまま進め、「クリーンな条件では英語教師の追加学習なしの性能で十分」を主な結果の一部として報告する
- 判断の目安: E0の全件評価(1000件)でもSI-SNR改善量が15dBを大きく超えるようなら1に進む。10dB前後まで下がるなら現行の条件のままでも適応の余地がある
- E0の全件評価の結果(2026-07-20): WSJ0-2mix教師19.66dB / Libri2mix教師25.37dB(詳細: [07_results.md](07_results.md))。目安に照らせば1(難しくする)が妥当
- 決定(2026-07-20 ユーザー承認): 1を採用する。JVSの混合音にWHAM! noiseを加えた「雑音つき日本語混合」を適応先にする(WHAM!の設定にならい、大きい方の話者に対する雑音のSNRを一様分布[-6, +3]dBで振る)。雑音の素材はWHAM!の学習・検証・評価の分け方を、本プロジェクトの学習・検証・評価に対応させ、話者と同様に重ならないようにする。残響を加えるかどうかは、雑音つきE0の結果を見て次の段階として判断する。クリーンな条件での結果(最初のE0)は「言語の違いだけでは障害にならない」ことを示す対照条件として発表に残す
- 雑音つきE0の結果(2026-07-20): WSJ0-2mix 0.57dB / Libri2mix 3.18dB / WHAMR! 9.09dB(詳細: [07_results.md](07_results.md))。クリーンな条件で学習した教師は雑音の下ではほぼ分離できなくなり、狙いどおり大きな違いが生まれた。残響の追加はいったん見送る(雑音だけで十分な難しさになっている)。教師はWHAMR!版に決定する

## DEC-014: 学習ジョブが約21時間停止していた問題と、再開機能の追加 (2026-07-23)

- 状態: 決定・対応済み
- 背景: 複数回のセッション再起動をはさんだあと状況を確認したところ、E1・E2とも**プロセスは生きているのにGPU使用率が0%で完全に止まっている**ことが判明した。W&Bの全履歴(サンプリングなしの取得)とチェックポイントの更新時刻から、両方とも2026-07-22の11:43〜12:03頃(確認時点から約21時間前)を最後に進捗が止まっていたと分かった。原因ははっきり特定できていないが、直近のカーネルログにNFSやメモリ不足の記録はなく、セッションの再起動が何らかの形でデータ読み込みのワーカーだけを壊し、メインプロセスだけが生き残った可能性を疑っている
- 決定: 止まったジョブは止めて再起動する。ただし当時の学習スクリプトには途中から再開する機能がなく、再起動すると最初からやり直しになり、E1はエポック26相当・E2はエポック11相当(合計30時間以上の計算)が失われる。そこで再開機能を先に実装してから再起動した(ユーザー承認)
- 実装内容:
  - `remixit/training.py`の`save_checkpoint`に、最適化手法・学習率スケジューラの状態などを任意で追加保存できるようにした。保存中に落ちても既存ファイルを壊さないよう、一時ファイルに書いてから置き換える方式にした
  - `scripts/train_supervised.py`(E1)・`scripts/train_remixit.py`(E2/E3)の両方に`--resume <チェックポイント>`を追加。最良値・改善のない回数もチェックポイントに保存し、再開時に引き継ぐ
  - 教師を逐次更新する設定(E3)では、教師の重みもチェックポイントに含め、再開時に正しい教師の状態を復元できるようにした
  - 停止していた実際のチェックポイントは、この機能を追加する前のスクリプトで保存されたもの(最適化手法などの状態を含まない)だったため、そうした古い形式のチェックポイントでも読み込めるよう、無い項目は初期値で補う作りにした(学習率スケジューラだけは位置がずれないよう、再開後のエポック数ぶん空回しして合わせる)
  - 小さな模擬データで「保存→再開→続きから学習」が正しく動くことを、新しい形式・古い形式のチェックポイントの両方で確認してから、実際のジョブに適用した
- 結果: E1はエポック27から、E2はエポック12から、それぞれ正しく再開できた(GPU使用率は両方とも98〜99%に復帰)
- 教訓:
  - 学習ジョブは実装の最初の段階から再開機能を作っておく。今回のように後から追加すると、既存のチェックポイントとの互換性を別途考える必要が生じる
  - `_step`だけで進捗を判断せず、経過時間そのもの(チェックポイントの更新時刻、W&Bの`_timestamp`)を必ず突き合わせる。W&Bの`history(samples=N)`は全件ではなく間引いた結果を返すため、直近の状態を見るときは`scan_history()`(全件)を使うか、`samples`を十分大きくする
  - GPU使用率が0%のまま何分も変わらないことは、プロセスが生きていても停止のサインになりうる。ひとめの`nvidia-smi`で判断せず、数秒おいて複数回確認する

## DEC-015: E2(静的教師)の実分離品質が伸び悩み、E3(逐次更新)を前倒しで開始 (2026-07-24)

- 状態: 決定・対応済み
- 背景: E1(教師あり上限)が完了し、評価用データでSI-SNR改善量13.23dBを確認した。同じタイミングでE2(RemixIT、教師固定)の途中経過(エポック22時点)を正解ラベルで評価したところ、**SI-SNR改善量−1.61dB**(入力の混合音そのままより悪い)という結果だった。一方、学習中に見ていた「教師との一致度」を示す検証損失は単調に改善し続けていた(エポック11の−19.61から22の−20.95まで)
- 分析:
  - 「教師との一致度」の改善と実際の分離品質の改善は別物であり、今回はっきり乖離した。教師(WHAMR!版)自体の性能が9.09dBとそれほど高くないため、教師の推定を混ぜ直して作った疑似的な混合音が実際の混合音と性質が異なり、生徒がその疑似的な混合音には適応しても実際の混合音にはうまく汎化していない可能性が高い
  - 教師を固定したまま(static)学習を続けるだけでは限界がある可能性が高い
- 決定: E1完了でGPU0が空いたタイミングを利用し、**E3(教師を逐次更新)を予定を前倒ししてGPU0で開始した**。E2(静的教師)はそのまま継続し、両者を比較する。教師の更新によって疑似混合音の質が実際の混合音に近づき、実分離品質が改善するかどうかを確かめる
- 運用の変更: 今後はE2・E3とも、学習ループの外から定期的に`eval_separation.py`で正解ラベルを使った実データ評価を行う。「教師との一致度」の検証損失だけで進捗を判断しない
- リスク: E2・E3とも実分離品質が改善しない場合、リミキシングによる自己学習そのものがこの条件(教師の性能が中程度・二重のドメインギャップ)ではうまく機能していないという結論になる。その場合は発表のストーリーを「RemixITの限界の実証」として組み直す(E0とE1の間を埋められなかったこと自体が知見になる)

## DEC-016: 雑音を第3の出力として明示的に分離する構成変更 (2026-07-27)

- 状態: 決定・対応済み
- 背景: E2(静的教師)が最終的にSI-SNR改善量−1.61dB、E3(教師逐次更新)も教師更新後で−4.8dB前後と、どちらもE0の教師そのまま(9.09dB)を下回った。生徒の出力を調べると、音量が入力混合音の90〜130倍という異常な大きさだった
- 分析:
  - SI-SNRは音量に依存しない(スケール不変)指標のため、音量の異常自体は理論上スコアに直接影響しない。実際に試しにmixture consistency(推定の和を入力に一致させる補正)を事後的にかけてみたところ、**むしろ悪化した**(E2: −1.61→−11.82dB、E3: −4.76→−8.56dB)。これは、混合音が「話者1+話者2+環境雑音」の3成分でできているのに生徒は2つしか出力しないため、差分に本物の環境雑音が含まれており、それを話者推定に配分すると雑音を混入させてしまうため
  - より筋の通る説明: RemixITの「混ぜ直し」は、話者2のスロットをバッチ内で別の録音のものに入れ替える。この時、話者2の推定には元々その録音の環境雑音の痕跡も含まれているため、入れ替え後の疑似混合音は「話者1の録音の雑音」と「話者2の録音の雑音」が二重に重なった、現実にはあり得ない分布になってしまう。生徒はこの不自然な二重雑音の混合音で学習することになり、本物の(雑音が1つだけの)混合音にはうまく汎化できていないと考えられる
- 決定: 雑音を第3の出力として明示的に分離する構成に変更する(ユーザー承認)
  - 生徒モデルの出力数を2→3に変更(`scripts/conf/model_small_3out.yaml`)。3つ目のスロットを雑音の推定として扱う
  - 教師は話者2出力のみのため、雑音推定は残差 ñ = 混合音 − (話者1推定+話者2推定) として計算する(`remixit/remix.py: split_teacher_estimate`)
  - 混ぜ直しでは話者2のスロットのみをバッチ内で入れ替え、雑音は入れ替えない(`remixit/remix.py: remix_with_noise`)。これにより疑似混合音の雑音は常に1つの録音由来に保たれる
  - PIT損失をN音源に一般化(`remixit/losses.py`)。評価スクリプトも、モデルの出力数が正解より多い場合(3出力を2正解と比較)に対応するよう一般化した(`scripts/eval_separation.py`)
- 検証: 小さな模擬データで、教師固定・教師逐次更新の両方(教師更新後に教師自体が3出力になるケースの再開機能も含む)が正しく動くことを確認してから、実際のE2/E3を新しい構成で再起動した
- リスク: これでも実分離品質が改善しない場合、この条件でのRemixITの限界として結論づける(DEC-015参照)。時間的な余裕(締切まで残り2週間弱)を踏まえ、これ以上の構成変更は行わない

## DEC-017: バッチサイズ拡張の検証(セカンドオピニオン経由) (2026-07-29)

- 状態: 実装・検証待ち(GPUが空き次第メモリ実測)
- 背景: DEC-016後もE2/E3の実分離品質が学習の進行とともに悪化する傾向が続いたため、`codex exec`(GPT-5.5)で独立したセカンドオピニオンを2回取得した
- 1回目の指摘(要点): DEC-016の診断(二重雑音)は妥当だが主因の一部。他に(a) バッチサイズ2はRemixITの理論的前提(誤差相関の平均化)にとって小さすぎる、(b) 雑音残差ñには教師の分離誤差・話者漏れも混じっており「汚い」疑似ターゲットになっている、(c) 3出力PITは話者と雑音のスロットを完全対称に扱うため役割が固定されない、という3点を新たに指摘された
- 2回目(バッチサイズ対応の相談): 選択肢を提示して比較した
  - (A) segment_secを短縮してbatch_sizeを上げる(1GPU内で完結、実装コスト低)
  - (B) 2GPU間でDDP+all-gatherしてリミキシングの実効バッチを上げる(実装コスト高、11日の締切には不向き)
  - (C) grad_accumだけ増やす(リミキシングの多様性には寄与しないため効果薄)
  - → セカンドオピニオンの結論: (B)は見送り、(A)を軸にAMP(自動混合精度)でメモリを浮かせてbatch_size=4を狙う。segment_secはいきなり2.0まで削らず、まず3.0で試す。3.0で入らなければ2.5、それでも駄目ならbatch_size=3を検討。三度目のフル再学習をいきなりやる価値は微妙だが、バッチサイズ2という理論的前提への弱点は重要なので、数時間〜1日の短い検証実験を1本入れる価値はある、との判断
- 決定: セカンドオピニオンの結論を採用する
  - `train_remixit.py`にAMP(autocast + GradScaler)を追加(`cfg["amp"]`で有効化、既定false)
  - 検証用config `scripts/conf/train_remixit_bigbatch.yaml`(batch_size=4, segment_sec=3.0, grad_accum=1, amp=true)を用意
  - DDPは実装しない
- 現状: コードの実装・ロジック検証(CPU・再開含む)は完了。GPUが3枚とも使用中(自分のE2/E3+他ユーザー)のため、実GPUでのメモリ実測(batch4×3秒が11GBに収まるか)は空き次第行う
- 次のアクション: メモリが収まることを確認 → 数時間〜1日の短い検証実験でtrendを見る → 明確に改善傾向が見えれば残り日数で本学習に切り替え、曖昧なら現行のE2/E3の結果で発表を組み立てる
- 実測結果(2026-07-29): batch_size=4, segment_sec=3.0, AMPありで**ピークメモリ6.91GB**(11GB中)と、変更前のbatch2×4秒(8.2-8.3GB)より余裕を持って収まることを確認した。GPU0(E2完了で解放)で短い検証実験を開始した(`exp/e2_bigbatch_check`、教師固定・静的教師のみでバッチサイズの効果を単独で見る)

## DEC-018: RemixITの追加チューニングを打ち切り、結果を確定させる (2026-07-30)

- 状態: 決定
- 背景: DEC-017のバッチサイズ拡張実験(`exp/e2_bigbatch_check`、batch_size 2→4・segment_sec 4.0→3.0・AMP)の経過を追ったところ、次の結果になった
  - 実データでのSI-SNR改善量: エポック9で+0.66dB(これまでの全実験を通じて最高値)→ エポック11(best.pth)で+0.34dB → エポック12(last.pth)で−0.29dB
  - つまりバッチサイズを上げても、「学習序盤にピークを迎え、その後実分離品質が悪化する」という現象そのものは解消しなかった。ピークの値が上がり(+0.66dB)、反転するタイミングが少し遅くなった(エポック9頃)だけである
- 分析: 3つの独立した設定で同じ形の現象が繰り返された
  1. 小バッチ・教師固定(E2, DEC-016後): ピーク+0.14dB → 悪化
  2. 小バッチ・教師逐次更新(E3, DEC-016後): ピーク+0.38dB → 悪化
  3. 大バッチ・教師固定(バッチサイズ拡張後): ピーク+0.66dB → 悪化
  - もはや偶然ではなく、この研究設定(教師の性能が中程度・言語+雑音の二重ドメインギャップ)における一貫した現象と見なせる。関連研究の調査結果([09_related_work_review.md](09_related_work_review.md))とも整合する
- 決定(ユーザー承認): これ以上の構成変更・チューニングは行わない。上記の繰り返し観測された現象を確定した知見とし、発表資料の作成に移る
  - 惜しい点: 学習スクリプトが「教師との一致度」を基準にチェックポイントを選ぶ仕組みのため、エポック9(実データでの最良値)の重みは、その後のエポック10・11で(教師との一致度の上では)上書きされ、復元できなくなった
- 対応(安全網、今後のため): `scripts/train_remixit.py`に、各エポックのモデル重みだけを`{out_dir}/epochs/epoch{N:03d}.pth`として個別に残す処理を追加した(optimizerの状態などは含めず軽量、1エポックあたり約20MB)。これにより今後は、どのエポックが実データ上のピークだったかを後から評価し直して確認できる。今回動いている実験(過去のコードで起動済み)には遡って適用できないが、今後の実験には有効
