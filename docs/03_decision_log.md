# 意思決定ログ (Decision Log)

プロジェクト研究A「RemixIT × TF-Locoformer によるシングルチャネル音源分離」の意思決定記録。
各決定は ADR(Architecture Decision Record)風に「背景 → 選択肢 → 決定 → 理由」を残す。

**成果発表期限: 2026-08-10**

---

## DEC-001: 研究テーマの大枠 (2026-07-20)

- **状態**: 決定
- **決定**: RemixIT の自己学習フレームワークに TF-Locoformer をモデルとして組み込み、シングルチャネル音源分離(音声強調)に取り組む。
- **背景**: 研究室仮配属のプロジェクト研究Aのテーマとして学生が選定。
- **理由**:
  - RemixIT はアーキテクチャ非依存と論文で明言されており、組み合わせは手法として正当。
  - RemixIT 原論文は軽量な時間領域モデル(Sudo rm -rf, 0.56M params)のみで検証 → TF領域 SoTA アーキテクチャで自己学習がどう振る舞うかは未検証であり、小さくても新規性がある。
  - TF-Locoformer は公式実装が公開されており実装リスクが低い。

## DEC-002: タスク設定(強調 vs 話者分離) (2026-07-20)

- **状態**: **決定 — (b) 2話者分離**
- **選択肢**:
  - (a) 音声強調(speech + noise の2出力)— RemixIT が設計された本来の設定。ノイズ推定の置換リミキシングがそのまま使える。
  - (b) 2話者分離 — TF-Locoformer の主戦場だが、RemixIT のリミキシング(ノイズだけ置換)を話者置換に読み替える拡張が必要。
- **決定**: 2話者分離に取り組む(ユーザー選択)。
- **理由・リスク認識**:
  - TF-Locoformer の主戦場であり、分離ベンチマークとの比較がしやすい。
  - リミキシングは「バッチ内で片方の話者推定スロットを置換して再混合」に拡張する。生徒の損失は PIT(置換不変学習)+ SI-SNR。
  - **関連研究に注意**: TF-Locoformer の筆頭著者 Saijo らによる Self-Remixing (ICASSP 2023) が、リミキシングベースの教師なし「話者分離」をすでに提案している(混合音再構成損失ベースで、RemixIT の音源レベル疑似ターゲット損失とは異なる)。本プロジェクトは「RemixIT 型(音源レベル疑似ターゲット+教師継続更新)× TF-Locoformer」として差別化し、発表では関連研究として必ず言及する。

## DEC-003: 使用コーパス (2026-07-20)

- **状態**: **決定 (2026-07-20 ユーザー承認)** — 教師 = 英語学習済み公開 TF-Locoformer、適応先 = JVS シミュ2話者混合(正解は評価のみに使用)、評価 = 話者 disjoint な JVS test で SI-SNRi。J-CHAT は余裕があれば試聴デモのみ。
- **重要な発見 (2026-07-20)**: ユーザー自身の既存プロジェクト `~/projects/jchat-sep` が、まさに TF-Locoformer × RemixIT の 1ch 話者分離を JVS(教師事前学習+定量評価)+ J-CHAT(実データ適応)で実施中。
  - 学習済み教師あり: `exp/teacher_jvs_1ch/best.pth`(SI-SNR 25.99 dB)
  - MonoRemixIT 実装・smoke テスト済み(テスト55件 pass)、JVS 本学習を起動できる状態
  - J-CHAT データ取得・JVS 前処理(話者disjoint分割)完了
  - → DEC-006 で「仕切り直し(新規構築)」と決定。ただしデータ資産・知見の参照は可

### 候補比較 (2026-07-20 検討)

| 観点 | (A) JVS シミュ混合 | (B) J-CHAT 実会話 | (C) Libri2Mix(英語) |
|---|---|---|---|
| 正解データ | あり(シミュなので SI-SNRi で定量評価可) | **なし**(DNSMOS・試聴のみ) | あり |
| RemixIT の適応ストーリー | 英語学習済み教師 → 日本語への**クロスリンガル適応**として明快 | 実環境適応として最も本物 | WSJ0→Libri のドメイン適応(先行研究の再現に近い) |
| データ準備コスト | 低(JVS は無償・軽量。16kHz 変換済み資産も NAS にあり) | 高(shard DL・2話者/重畳率での選別・リサンプルが必要) | 中(LibriSpeech DL + 混合生成) |
| 教師の調達 | MERL 公開 TF-Locoformer(WHAMR! 2話者)をそのまま OOD 教師に使える | 同左だが教師の劣化が激しい可能性 | 公開チェックポイント多数 |
| 8/10 リスク | **低** | **高**(選別実装+評価が定性的) | 中 |
| 発表の映え | 「英語モデルを正解なしで日本語化」— 分かりやすい | 実データデモは強いが数字が出ない | 手堅いがストーリーが借り物 |

- **推奨(提案)**: **(A) JVS を背骨に据える**。教師 = MERL 公開 TF-Locoformer(英語・WHAMR!)、適応先 = JVS シミュ2話者混合(ラベルは評価のみに使用)、評価 = 話者 disjoint な JVS test で SI-SNRi。
  余裕があれば (B) J-CHAT の少数セグメントで「実会話への適用デモ(試聴)」をストレッチゴールとして追加。(C) は新規性・発表の観点で見送り。
- **前提**: 計算資源は RTX 2080 Ti (11GB) ×3(DEC-005)。WSJ0 系(WSJ0-2mix, WHAM!, WHAMR!)は LDC ライセンスが必要で、研究室保有かは要確認。
- **提案**:
  - 教師(OOD 事前学習): **公開学習済みチェックポイントを利用**して事前学習コストをゼロにする(例: SpeechBrain sepformer-wsj02mix、Asteroid の ConvTasNet/DPRNN 等、WSJ0-2mix 学習済み・8kHz)。
  - 生徒(ドメイン内適応先): **Libri2Mix**(LibriSpeech ベース、無償生成可能)。train-100・8kHz・min 版で約 14k 混合音。RemixIT ではラベルなし混合音としてのみ使用。
  - 評価: Libri2Mix test で SI-SNRi / SDRi。ベースライン = 教師のゼロショット性能、上限 = 教師あり学習した TF-Locoformer(計算が許す範囲の縮小構成)。
  - ストーリー: 「WSJ0 ドメインの既製モデルを、ラベルなしの Libri2Mix 混合音だけで TF-Locoformer に蒸留・適応させる」= RemixIT のドメイン適応設定の分離版。

## DEC-004: 実装基盤(ESPnet vs 独自実装) (2026-07-20)

- **状態**: **決定 — ESPnet を改造**
- **決定**: TF-Locoformer 公式(ESPnet-SE パイプライン)をベースに ESPnet を改造する(ユーザー選択)。
- **理由・リスク認識**:
  - ESPnet のレシピ資産(Libri2Mix データ準備、評価スクリプト、TF-Locoformer 設定)をそのまま使える。
  - RemixIT の教師-生徒ループ(リミキシング・教師更新)は ESPnet 標準 Trainer に乗らないため、カスタム Trainer / 学習スクリプトの追加実装が必要。ここが実装リスクの中心。
  - 緩和策: データ準備・モデル定義・評価は ESPnet に乗せ、RemixIT ループ部分だけ独立したスクリプトとして書く(ESPnet 内部への侵襲を最小化)。

## DEC-005: 計算資源の確定 (2026-07-20)

- **状態**: 決定(事実確認)
- **内容**: 研究室サーバー(この作業マシン)= NVIDIA RTX 2080 Ti (11GB) ×3、RAM 125GB、36コア、NAS (kiso-qnap5) 空き 52TB。
- **含意**:
  - TF-Locoformer は **Small (5.0M) 以下の構成**、8kHz、セグメント4秒、batch 2〜4(+勾配累積)が現実ライン。Medium はメモリ・時間的に厳しい。
  - DNS 規模(2700h)の学習は不可能 → 教師は公開チェックポイント利用(DEC-003)。
  - GPU 3枚は「並行実験3本」(例: ベースライン/RemixIT/アブレーション)に使うのが期限的に有効。

## DEC-006: 既存プロジェクト jchat-sep との関係 (2026-07-20)

- **状態**: **決定 — 仕切り直し(proken-A として新規に作り直す)**
- **背景**: `~/projects/jchat-sep`(TF-Locoformer × RemixIT、JVS+J-CHAT)が既に実装・教師学習済みの状態で存在する。
- **決定**: jchat-sep は元々別の題材(2ch エゴセントリック)から途中で切り替えた経緯があるため、proken-A では**仕切り直して新規にプロジェクトを組み直す**(ユーザー決定)。
- **含意**:
  - コードは proken-A で新規に構築する(DEC-004 の ESPnet 改造方針は維持)。
  - jchat-sep で得た**知見は参照してよい**(学習率スケジュールの教訓、batch≥2 制約、J-CHAT の歩留まり実測、RemixIT 検証損失の解釈など。jchat-sep/docs/decisions/ 参照)。
  - NAS 上のデータ資産(J-CHAT shard、JVS 16kHz 変換済みデータ等)の再利用は妨げない。
- **期限の確認**: **8/10 が正**(jchat-sep todo.md の「8月下旬」記載は旧情報または別件)。

## DEC-007: 教師の言語ミスマッチへの対処(英語教師で大丈夫か) (2026-07-20)

- **状態**: 決定(設計方針)
- **背景**: 「教師も日本語モデルでないとうまく分離できないのでは」という懸念(ユーザー提起)。
- **分析**:
  - 話者分離の主要な手がかり(ピッチ・声色・調波構造)は言語非依存性が高く、英語教師のゼロショットでも一定の分離は期待できる。ただし劣化は見込む。
  - RemixIT は教師が不完全な状況をむしろ前提とした設計であり、原論文は教師 SI-SNR が 5dB 未満の低品質推定でも生徒が平均 +2dB 程度改善することを示している(Fig. 5)。ただし教師 SI-SNR が −10dB 以下で破綻している領域では生徒も学習できない(Fig. 3)。
  - 教師を最初から日本語で本格的に fine-tune すると、ドメインギャップ(=研究主題)が消えて「適応」の意味がなくなる。言語ミスマッチは排除すべきノイズではなく、**制御された実験変数**として扱う。
- **決定**:
  1. **E0(教師ゼロショット評価)を Go/No-Go ゲートにする**: 英語教師(MERL 公開 TF-Locoformer)を JVS シミュ test でゼロショット評価し、SI-SNRi ≥ 5dB 程度なら Go(そのまま RemixIT へ)。
  2. **No-Go 時のフォールバック**: 少量のラベル付き JVS シミュ(例: 全体の10%)で教師を軽く fine-tune してから RemixIT を行う。この場合は「半教師ありドメイン適応」(RemixIT 論文にも同設定あり)として発表を再構成する。研究として依然成立する。
  3. どちらに転んでも「教師の初期品質と生徒の改善幅の関係」として発表で語れるため、E0 の結果自体が成果物になる。

## DEC-008: サンプリング周波数・教師チェックポイント・混合条件 (2026-07-20)

- **状態**: 決定
- **決定**:
  1. **8kHz で統一**。MERL 公開の分離用チェックポイント(WSJ0-2mix / Libri2mix / WHAMR!)はいずれも 8kHz 学習のため、JVS(16kHz 変換済み資産)を混合生成時に 8kHz へダウンサンプルする。
  2. **教師候補は WSJ0-2mix 版と Libri2mix 版の両方を E0 でゼロショット評価**し、JVS test で良い方を教師に採用する(推論のみなのでコストは小さい。「どの英語教師が日本語へ転移しやすいか」自体が発表で語れる副次結果になる)。WHAMR! 版は残響前提のため優先度低。
  3. 混合条件: 別話者ペア、SNR 一様 [-5, 5] dB、min 長 fully-overlapped、train 20k / valid 1k / test 1k。
- **確認済みの事実**: MERL リポジトリ(Apache-2.0)は WSJ0-2mix / Libri2mix / WHAMR! / DNS の学習済みモデルを egs2 の exp 配下で提供。ローカル環境(conda `tflocoformer`: ESPnet 202402 + TFLocoformerSeparator + CUDA 可)で動作確認済み。JVS は 16kHz 変換・話者 disjoint 分割済み資産(train 10398 / valid 1299 / test 1300 発話)を再利用する(DEC-006 の範囲内)。

## DEC-009: ストレージ配置(ローカルディスク満杯への対処) (2026-07-20)

- **状態**: 決定
- **背景**: 研究室サーバーのルートFS(1.8TB)が **100% 満杯**(空き199MB)と判明。主因は共有ユーザー群のデータ(/home 合計540GB+読めない領域)であり、勝手に削除できない。このままではデータ生成・チェックポイント保存が即座に失敗する。
- **決定**: 本プロジェクトの大容量物はすべて NAS(/mnt/kiso-qnap5/kueki/proken-A、空き52TB)に置く。
  - `data/` `exp/` はリポジトリからのシンボリックリンク → NAS
  - MERL リポジトリ(教師 ckpt 含む)も NAS の `third_party/` へ
  - 8kHz 音声は軽量なため NAS 越しの学習 I/O は問題にならない見込み
- **残課題(ユーザー対応)**: サーバー管理者・研究室メンバーへディスク満杯を連絡することを推奨(学習とは独立の問題として)。
